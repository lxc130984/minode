### D-01 不写 Lisp 解释器

- **决策**：保留 Lisp 的 `eval/apply` 思想，但实现为领域专用的应用树求值器；不引入任何 Lisp 库，也不做文本 s-expression 层。
- **背景**：树是玩家可编辑的一等 AST；UI 需要在**求值前**就显示每个节点的静态指称（`[..]`）；内容是数据（`id` 是存档契约）；局面要能序列化与撤销。
- **后果**：通用 `eval` 循环能做的事我们做不了（闭包、变量、宏）；换来的是内容纯数据、显示零副作用、存档/undo 直接吃树。加「语言特性」前先问：能不能用 `NodeDef` 字段或配方数据表达。

### D-02 点击 = 单节点 eval

- **决策**：点 chip 只 eval 被点节点（符号无响应、函数命中配方即产出进背包）；子节点**只提供静态结果**，不被触发。
- **背景**：增量点击游戏需要「点了就有反馈」；递归求值会把一次点击放大成整棵树的经济活动，且与静态 `ret` 的双重语义打架。
- **后果**：`ret` 可以保持纯静态（无副作用），因此能全量/增量重算并直接用于显示；「批量生产」必须另做机制（见 09 篇路线），不能靠点击递归。

### D-03 撤销树

- **决策**：历史是**树**不是栈：中间做新操作 = 分叉；可点任意分支穿梭；`MAX_ENTRIES = 300`；历史不写进存档。
- **背景**：沙盒类游戏玩家经常「试一下再回来」；线性 undo 会抹掉未来。
- **后果**：每个历史节点存一份**完整局面快照**（不做差分）→ 内存换实现简单；读档/重置重建单节点历史；快照复用存档序列化，格式变化要同时考虑两边。

### D-04 悬停只标父节点

- **决策**：悬停某 chip，只给它**父节点**加下划线（`#e6e6ea`、2px、offset 4px）；不标祖先链、不标同级。
- **背景**：早期做过「祖先链底纹 + 同级点线」，噪声大、每次悬停要写十几个键。
- **后果**：一次悬停只影响两个节点（性能与视觉都干净）；代价是「这节点属于哪条链」需要靠层级竖线与缩进自己看。

### D-05 拖拽：DOM 媒介 + store 单写者

- **决策**：SortableJS 只负责手势与预览；落位从事件读「节点 id / 源属主 / 目标属主 / `newIndex`」，由 `store.handleTreeDrop` 在**模型**上搬迁；所有结构写入走 `writeList`（**先摘后插**）。
- **背景**：旧实现把每列回写数组直接写回模型 → 跨列表移动退化成「复制到目标、原处残留」→ 同一节点出现在两个列表（重复 `data-node-id`）→ Vue keyed diff 与 SortableJS 元素映射双双失配：**拖一次后再也拖不动 + 配方乱检测**，且折叠展开一次会暂时好转。
- **后果**：**不变量**：同一节点对象在树中只出现一次；不能读 DOM 顺序（vue-draggable-plus 在 `on-end` 前已复位 DOM）；物品克隆的 `end` 发在源容器（侧栏）上；落位失败必须能自愈（`requestTreeRebuild`）。

### D-06 派发表与增量归一化

- **决策**：注册表构建期预编译 `(模式, 签名) → 配方` 哈希表，归一化与点击求值共用；结构变更只重算「受影响列表属主 + 祖先链」。
- **背景**：旧路径是「每个节点 × 每条配方现场拼签名串线性比较」，且归一化每次全树后序。
- **后果**：内容规模上来后仍是 O(1) 派发；**代价**：新增/修改配方相关字段必须同时更新构建期索引；`parentOf` 索引成了必备设施（拖拽摘挂也依赖它）。

### D-07 语法高亮

- **决策**：按**种类**上色（函数=琥珀 `#e6b04f`／符号=青 `#5fc3a6`／工具=紫 `#b98fe0`／未注册=灰 `#8a8a95`；结果=绿 `#94d47f`、未解析=橙 `#e09a6a`），深度只决定亮度（`--dim` 8/15/22/28/34%）。
- **背景**：用户要「像写代码一样」的高亮；早期美术规范禁止饱和色，这条以本决策为准放宽（仍限灰阶底 + 低饱和）。
- **后果**：`color-mix()` 的百分比**不能写 `calc()`**（整条声明静默失效）；深浅靠一个 `--dim` 变量统一控制，加层数不用改色表。

### D-08 `×` = 挖取（带工具门槛）——**已被 D-12/D-13 部分取代**

> 2026-10-10 撤回：工具门槛不符合「节点应该可以被随便操作」这条直觉；`×` 改为**自由**的节点操作
> （见 D-12）。`NodeDef.mine`、`planMine`、镐物品全部删除，`toolClass` 字段保留（将来给工具**节点**用）。

- **决策**：节点右侧 `×` 正式语义是**挖取**：产出 1 个对应物品，子节点上移。门槛：`NodeDef.mine` 缺省=徒手可挖，`false`=不可挖取，`{ tool }`=需要手持该 `toolClass`。当前内容：机器（矿井/冶炼炉/锻炉/轧机/装配台/发动机厂）需**镐**，原料徒手可挖。镐作为物品存在（`toolClass: 'pickaxe'`），**不消耗**。
- **背景**：所有节点都能拆不符合沙盒直觉；工具门槛让「手持什么」有第二层意义（第一层是 eval 通道）。
- **后果**：`×` 从「拆解」改称「挖取」（行为同：返还物品 + 子节点上移）；挖不动时要给**提示**而不是静默失败；将来「更好工具 → 更多产出」由 `MinePlan.count` 扩展；工具本身靠初始补货发放（**合成系统尚未存在**，见 09 篇 M9）。

### D-09 方括号与返回值分色

- **决策**：`[` `]` 用中性暗色（跟随深度衰减的灰），括号内的值用结果色（绿）；`[?]` 用橙色。
- **背景**：用户反馈「返回值和 `[]` 同色 → 没有色彩立体感」。
- **后果**：chip 里 `.chip-ret` 拆成 `.chip-bracket` + `.chip-ret` 两个 span；状态类（`is-idle`/`is-unknown`）继续只作用于值部分。

### D-10 物品栏/背包改矩形槽

- **决策**：物品栏与背包统一为**矩形槽**，与节点 chip 同款字符样式（等宽、行内文本 + 数量角标），不再用 30×30 小方块。
- **背景**：小方块里长名字（发动机厂/装配台）挤成一团，且字符渲染被字号/居中断裂。
- **后果**：槽宽由内容决定（`min-width` 对齐），列数/换行规则进 06 篇 §8；拖拽 `handle` 仍是 `.inv-slot`；物品按 **资源/方块/工具** 三色高亮（复用 D-07 色相）。

### D-11 决策入台账

- **决策**：任何「用户拍板」或「会长期影响代码形状」的选择，追加到本文件；实现细节留在 01-07 篇。
- **背景**：项目由人 + AI 协作，决策散在对话里会丢失，复查时无从对照。
- **后果**：每次大改动前先看本台账；若与旧决策冲突，先改台账再改代码。

### D-12 `×` 回归自由节点操作

- **决策**：撤回 D-08 的工具门槛。`×` = 「收起」：把该节点**本身**放进节点背包（子节点上移），不做任何门槛判定。
- **背景**：节点操作应当无条件；门槛把「整理树」这件高频动作卡住了。
- **代价**：`NodeDef.mine`/`engine/mine.ts`/镐物品全部删除；将来若要门槛，应做成别的机制（例如节点自带的“锁”而不是手持工具）。

### D-13 删除 item 概念：节点背包 + 资源仓库

- **决策**：不再有「item」这一层。物品栏拆成两个容器：
  - **节点背包**：只放 `GameNode`，**里面的东西全部可放置**（本质上就是「另一个存放节点的面板」，
    树 ↔ 背包之间是**移动**关系，不是「物品→节点」的转换）；
  - **资源仓库**：只放**不可放置**的资源（铁/钢/板/零件/引擎……），从简设计——一个「名称 × 数量」列表，
    没有槽位、没有光标、不参与拖拽。
- **背景**：旧模型里 item 既承载「可放置」（铁矿→铁矿石节点）又承载「纯资源」（铁），两套语义混在一层里；
  玩家要区分「这格能不能放」全靠猜。按「能不能放置」拆成两个容器后，每个容器内部语义单一。
- **后果**：
  - `ItemDef`/`ItemStack`/`Slot`/`places`/`stack` 全删；配方 `out` 里的 id 是**资源或节点类型**，
    由 `registry.node(id)` 是否存在决定去向（节点 → 背包；否则 → 仓库）；
  - 存档升 v2（`nodeBag` + `resources`），v1 旧档按同一规则迁移；
  - 节点背包里的节点**没有子节点**（收起/拖动时子节点上移），因此可以逐格展示；
  - 求值通道从 `item:<id>` 变为 `node:<type>`（`class:<toolClass>` 保留，挂到 `NodeDef`）。
- **已知问题（待下一轮体验微调时解决）**：**背包 → 树的拖拽**在 vue-draggable-plus 下被
  SortableJS 判成「背包内部重排」（实测：`from/to` 都是 `.bag-grid`），所以拖不出背包。
  当前可用路径：**双击背包格**（放到根层末尾）、左键选中/右键拿起、树内拖拽、树 → 背包拖拽（✔）。
  store 侧落位逻辑本身正确（直连 `applyDrop({from:{kind:'bag'},…})` 返回 true 且模型正确）。

### D-14 节点背包堆叠 + 特殊节点面板（箱子）

- **决策**：
  1. **背包格放堆**：背包里的节点都没有子节点，所以 `type` 就是它的全部身份 → 一格 = `NodeStack { type, count }`
     （上限 `config.nodeStackLimit = 64`，同类先并堆、再占新格）。放入 / 取出 / 拖拽都以「1 个」为粒度。
  2. **特殊节点**：`NodeDef.panel`（当前只认 `'storage'`）——点击这种节点 = **打开浮动面板**，不做配方求值。
     首个落地的是**箱子**（`chest`，只存节点，`config.chestSize = 27`）；资源仓库无限，所以箱子不是资源容器。
  3. **面板呈现**：MC 风格浮动窗口，`absolute` 定位在右侧主区右上（`width: min(520px,62%)`、`max-height: 60vh`），
     **不铺满**右半边；左侧节点背包 + 资源仓库保持可见可用；右上角 `×` 关闭。
- **后果**：
  - 背包数据结构从「节点实例数组」变成「堆数组」→ **存档 v3**（`nodeBag` 存堆；`containers` 不按 id 存，
    而是挂在节点的存档条目上（`SaveNode.chest`），因为 **id 不入档**，按 id 存读档后必然丢内容）；
  - 箱子的内容属于「带内容的节点」，它被收起时内容一并回背包（装不下则整次拒绝）；
  - 面板状态（`panel`）是**瞬态**，不入存档；带内容的节点在树上用一个低调的 `▣` 标记；
  - 工作台（合成）等后续面板复用同一机制，**但没有设计之前不落地**（不做空壳 UI）。

### D-15 背包绑定落点 + 指针落区检测

- **决策**：
  1. **节点背包绑定一个落点**：默认是**放置界面**（树的根层）；打开某个面板时绑定到那个容器（当前 = 箱子）。
     双击背包格 = 把 1 个节点放进**当前绑定落点**（不再需要「存入手持」按钮，已删除）。
  2. **拖到哪儿就放到哪儿**：从背包拖出的节点，按**指针释放位置**决定去向——
     落在浮动面板上 → 进该容器；落在树列表上 → 在该列表末尾变成节点；落在背包上 → 背包内换位。
     从树上拖出的节点同理（落在面板上 = 存入容器）。
- **背景**：SortableJS 的跨容器落点在「背包 → 树」方向被判成背包内重排（D-13 的已知问题），
  与其和它的内部状态缠斗，不如**自己判断落区**：事件里现成有 `originalEvent.clientX/Y`，
  `elementFromPoint` 一下就知道玩家把节点丢在哪儿了——符合「手动拖一个节点去放置」的直觉。
- **后果**：
  - 落区判定在 `utils/tree-drop.ts`（`pointerOf` / `zoneAt`），路由在 `store.handleTreeDrop`；
    树内移动仍然用 SortableJS 给的精确 `newIndex`（落区检测只用于跨区）；
  - 拖到树上时插入**该列表末尾**（要精确位置就在树内再拖一次）；
  - 面板位置：紧贴主区左缘（与左侧背包之间只留原有缝隙），盖住放置界面无妨；宽度 `min(560px, 74%)`。

### D-16 容器交互规范：背包锁定 + 蒙灰 + 两容器转移

- **删除** D-15 的「按指针落区决定去向」——边界情况太多。改为 MC 式：
  **打开容器面板 → 节点背包锁定到那个容器**（双击/单击续转/滚轮都往它送），**放置界面蒙一层灰**且不可交互，
  点灰层 = 关闭面板（回到「背包 ↔ 放置界面」的默认绑定）。
- **浮动面板可拖动**：`pointerdown` 抓住标题栏（`×` 除外）+ `setPointerCapture` 跟手，松手停住；
  纯原生指针事件，**不需要第三方库**（拖拽库是给列表排序用的，窗口拖动只有几十行）。
- **两个容器界面之间的节点转移**（本规范对「任意两个容器」通用，当前 = 节点背包 ↔ 箱子）：
  1. **双击**某一格 → 转移 1 个；此后**继续单击同一格** → 每点一次再转移 1 个（该格成为「活动格」，
     点别的格则改选/改活动格）；
  2. **拖到另一边 = 整组转移**（整堆一次过去）；
  3. **滚轮**滚过某一格 → 转移 1 个（同样把该格设为活动格）。
     方向由「哪一边是活动源」决定：背包格 → 当前绑定容器；容器格 → 节点背包。
  - **拖拽的落点判定只看"来源/目标是哪种列表"**：容器网格也是 Sortable（`data-list="chest"` + `data-owner` +
    每格 `data-bag-index`），所以「背包 → 面板」= 整组存入、「面板 → 背包」= 整组取出，都**不看坐标**；
  - ⚠️ 容器格必须带 `data-bag-index`，否则来源解析失败（拖拽会变成"什么都没发生"——这是踩过的坑）；
  - ⚠️ **落点格号只能问指针**：跨容器拖拽时 SortableJS 的 `newIndex` 会被 vue-draggable-plus 的复位抹掉
    （plan 里目标会退回"背包自己"），所以"放到哪一格"用 `elementFromPoint → closest('[data-bag-index]')`
    取——这只是**局部取格号**，不是 D-15 那种"按坐标决定去哪个区"的路由；
  - ⚠️ 整组转移必须**先试算再一次性提交**（`bagPlaceAt` + `bagTakeAt`）：否则会出现
    "背包加了一整堆、箱子只少了一个"的计数不一致（=凭空的物品复制）；
  - 面板打开（或容器侧发起拖拽）时，树里的空落点条**不显示**（`is-locked` / `is-panel-drag`），
    否则玩家会看到"被锁住的放置界面还在响应拖动"。
- **落区判定的去向**（写死，不看坐标）：树内移动仍走 SortableJS 的精确 `newIndex`；树 → 背包 = 收起 1 个；
  **背包 → 任意处**（有面板时）= 整组进容器，无面板 = 背包内换位；**容器 → 背包** = 整组回背包。

### D-17 容器交互照搬《我的世界》

- **决策**：容器（节点背包、箱子）之间的搬动**不再用列表排序**，改成 MC 那套：
  1. **固定格位**：两个网格都是定长 27 格，格与格之间不排序、不挤压（此前 SortableJS 会互相挪位，已移除）；
  2. **光标携带**：`pointerdown` 拿起整格 → 光标跟着鼠标 → 松在目标格放下（空格=放入 / 同类=并堆到上限 /
     异类=交换，换出来的那堆继续拿在光标上）；松在原格 = 继续拿着；松在**放置界面**上 = 整堆落成 N 个根节点；
     其余落空 = 继续拿着；
  3. **快捷键（MC）**：左键 = 拿起/放下；**Shift+左键 = 整堆送到另一边**（背包 → 当前容器面板；无面板 → 放置界面）；
     右键 = 空手拿一半 / 手持放 1 个；双击 = 收集同类到光标；滚轮 = 送 1 个到另一边（本作扩展）；
  4. **放置界面**：仍用 SortableJS 做**树内**移动；树 → 背包装箱入口保留 `×`（收起），不再有"拖到背包"的跨容器拖。
- **后果**：
  - 与 SortableJS 的跨容器缠斗彻底结束（D-13/D-15/D-16 那一串坑随之作废）；`utils/tree-drop` 只剩树内移动；
  - 堆在树里会**展开成 N 个节点**（树没有堆的概念），所以"整堆放到放置界面" = 一次多出 N 个根节点；
  - 关掉面板后光标上若还拿着东西，会一直跟着鼠标 —— 按 MC 的规矩，点一下目标格放下即可（想清空就点回原格/背包）。

### D-18 还原：容器交互回到 D-16

- **决策**：实测后判定《我的世界》那套（固定格位 + 光标携带 + Shift/右键/双击收集）**不适合本作**，
  还原为 D-16：**双击起转 1 个 → 之后单击同一格继续转 1 个**；**滚轮转 1 个**；**拖到另一边 = 整组转移**；
  单击 = 选中（手持）；右键 = 拿起/放下（与光标交换）；「放到哪一格」用指针那一格。
- **背景**：MC 的交互依赖「鼠标手」这个强概念（拾起→搬运→放下），在只有两栏、格数很少的容器面板里
  反而比「双击/滚轮 + 整组拖」啰嗦；而且它逼着玩家两次操作才能放一格。
- **保留下来（不回滚的部分）**：
  - D-16 的**固定落点修复**（指针取目标格号、整组转移先试算再提交、容器格带 `data-bag-index`）；
  - 面板可拖动、打开面板时放置界面蒙灰且落点条隐藏（D-16 的这部分一直有效）；
  - 面板网格与背包网格**仍是 Sortable 容器**（拖拽整组依赖它），但**面板打开时树是锁的**。
- **教训**：容器交互在「像 MC」和「够快」之间要选后者；下次改交互先问「一步能不能完成」。

### D-19 容器网格改原生拖拽（格位固定）

- **决策**：容器（节点背包 / 箱子）里的格子**在拖动过程中绝不移动**——用原生 HTML5 拖拽
  （槽位 `draggable` + `dragstart` 只记「从哪一格拖的」），不再让 SortableJS 搬 DOM 做预览。
- **背景**：D-16/D-18 期间容器网格仍是 Sortable 容器，拖动时它会**把自己的 DOM 挪来挪去**，
  于是其余格子被挤位/移位（用户明确反馈：要固定位置）。
- **后果**：
  - **同容器**内放下 = 两格**交换**（不是插入+挤位）；落在原格 = 无操作；
  - **跨容器**放下 = 整组转移，落在**指针那一格**（`dropSlotDrag` 用目标格号 ✓）；
  - 树**内部**移动仍用 SortableJS（那里需要预览，手感是对的）；
  - 副作用清单：容器拖拽不再有 SortableJS 的 ghost/chosen 样式，改用 `.is-drag-source` 淡化源格；
    跨容器拖拽不再依赖 SortableJS 的 `newIndex`（那条链上的坑全消失）。

### D-20 格位固定改用 VueDraggable 的 `sort: false`

- **决策**：容器网格**继续用 `VueDraggable`**（不自己写原生拖拽），用它自带的选项
  **`:sort="false"`**（README：_Allow list items to be sorted within container_，默认 `true`）——
  容器内部**不排序、格位固定**，但**跨容器拖拽与「拖到放置界面」照常工作**。
- **背景**：D-19 用原生 HTML5 拖拽虽然做到了格位固定，但**和放置界面彻底断了**：
  树那边是 SortableJS 的拖拽体系，两边不是同一套事件/数据通道，玩家没法再把节点从背包拖进树。
  自写一套跨组件拖拽协议 = 把库已经解决的问题重新踩一遍。
- **据此而来的落位路由**（`handleTreeDrop`，全部按 plan 判定，不看坐标）：
  - 背包 → 容器格 = **整组转移**落到该格（格号问指针）；
  - 背包 → 树列表 = **整堆落成 N 个节点**（`placeWholeBagStackAt`，树里没有堆）；
  - 背包 → 背包 = 无操作（容器内不排序，拖回原处即无事发生）；
  - 容器 → 背包 = 整组回背包指定格；
  - 树 → 树 = `applyDrop`（原有精确 `newIndex` 逻辑）；
  - 树 → 背包 = 收起 1 个。
- **教训**：能在库里用选项解决的，不要自己造协议；「格位固定」这一条 `sort:false` 就够。

### D-21 「格位固定」= 掐掉插入预览（不是禁止拖动）

- **澄清需求**：玩家要的是**拖动过程中其它格不被推挤**，同时**本容器内仍然能拖动**（落点 = 交换）。
  D-20 的 `sort:false` 理解错了：它让容器内**彻底不能拖**，而且挤压照旧。
- **做法**（库内能力，不自己造协议）：
  1. 容器网格仍是 `VueDraggable`（`sort` 保持默认 `true` → 能拖）；
  2. 两个容器网格挂 **`:on-move="guardContainerPreview"`**：目标是**容器**时返回 `false`
     —— SortableJS 于是**不做插入预览**（DOM 不重排 → 其它格一格不动），但拖拽照常进行、`end` 照常上报；
     目标是**树**时返回 `true`（树那边仍要正常预览，跨到树里放置不受影响）；
  3. 落点**格号一律问指针**（`cellIndexUnderPointer` / `containerUnderPointer`），落下时在模型上结算：
     同容器 = `swapSlots`（两格交换）、跨容器 = `transferWholeStack`（整组落到该格）、落到树 = `placeWholeBagStackAt`（整堆落成 N 个节点）。
- **实测**：拖动中容器 27 格坐标数组**完全一致**（10 次 dragover）；容器内放下 = 只有两格互换（`0:mine ↔ 5:engine_plant`）；
  跨容器拖拽仍把整堆送到指针那一格；背包 → 树仍整堆落树。
- **教训**：「格位固定」说的是**预览/布局**，不是**拖拽能力**；能用库的 `on-move` 表达就别关掉整个排序。

### D-22 拖拽层重写：容器永不预览、落点只看指针、放树只放 1 个

- **三个 bug 的根因**：
  1. 拖进放置界面一口气放十几个 —— 我之前把「整堆落成 N 个节点」当特性（`placeWholeBagStackAt`），
     **拖一次 = 放 1 个**才对；
  2. 挤压没解决 —— 之前只挡了「容器 → 容器」的插入预览，**容器 → 树**那次仍让 SortableJS 把元素搬出容器做预览，
     源容器的格子因此照旧被挤位；
  3. 拖到箱子里却被放进树 —— 落位用的是 **SortableJS 上报的目标（`plan.to`）**，而它在复位/掐预览之后并不可靠。
- **重写后的唯一规则**（`utils/tree-drop.ts` + `store.handleTreeDrop`）：
  1. **容器网格一律不预览**（`:on-move="() => false"`）→ 任何由容器发起的拖拽，**两个容器的 DOM 都不动**（无挤压）；
  2. **落点一律问指针**（`zoneUnderPointer`：`elementFromPoint` → 背包格 / 容器格 / 树的哪个列表的哪个位置），
     SortableJS 的 `plan` 只用来确定**源**（DOM 没动，源必然可靠）；
  3. **放下即结算**：同容器 = 两格交换；跨容器 = 整组转移到指针那一格；
     **落到放置界面 = 只放 1 个节点**（`placeOneFromBagAt` 用 `bagTakeAt(..., D(1))`）；落空 = 什么也不做；
  4. 树内部移动仍走 SortableJS 的精确 `newIndex`（树那边要预览，是另一套、没动）。
- **实测**：一次拖拽 = 根层 +1（`矿井×2 → ×1`，再拖再 +1）；拖到容器格 = 整组落在那一格且**不进树**；
  容器内 = 只两格互换；拖动中容器格位数组不变。
- **教训**：跨组件拖拽只有**一个**权威（这里是"指针"）时才可推理；让库和我各判一半必然互相打架。

### D-23 容器改「并排列」：挤压只纵向、跨列改交换、落点全部看指针

- **用户的诊断（对的）**：容器原来是一个 27 格的大网格，插入一格会让后面所有格
  **同时横向 + 纵向**乱跳 —— 看着像"整列都在动"。挤压本身没错，错在**网格换行**。
- **改法**：容器拆成 **3 个并排的纵向列表**（`SLOT_COLUMNS=3 × SLOT_ROWS=9`，见 `utils/container-layout.ts`），
  存储仍是扁平数组（列优先 `index = col*9 + row`）。于是：
  1. SortableJS 的插入预览回归（列内让位 = **只向上/向下**，整齐可预期）；
  2. **同列**落位 = 插入式搬动（其它格在本列内纵向让位，用户要的"挤压"）；
  3. **跨列**落位 = 两格**交换**（不做跨列插入 —— 那会把整列挤到隔壁去）。
- **落点规则（D-22 的延续与修正）**：容器/背包来源的拖拽**一律按指针结算**
  （`slotUnderPointer` = 格；`treeZoneUnderPointer` = 树列表 + 插入位），因为
  vue-draggable-plus 会在 `on-end` 前复位 DOM、SortableJS 的 `plan` 在容器内部不可信；
  只有**树内部**的移动仍用 `plan` 的 `newIndex`（树允许预览，值可靠）。
- **背包 → 树 = 复制 1 个**：语义上就不是 SortableJS 的跨表"搬移"，所以由指针驱动
  （`placeOneFromBagAt(..., D(1))`），别指望目标列表接受一个异类元素。
- **修过的坑**：树的 `handle=".chip"` 会把背包格（`.bag-slot`）判拒 → 放宽为 `.chip, .bag-slot`。
- **实测**：三列并排（列 x 坐标 [239,322,386] 恒定）；同列 1→4 = `mine` 落在第 4 格、后三格依次下移；
  跨列 = 两格交换且其它列不动；背包 → 树拖拽 = `矿井×2 → ×1` + 根层 `矿井[?]` 一个（hint 提示）；跨容器 = 整组转移。
- **教训**：**网格换行**才是挤压失控的根源；把"二维让位"拆成"一维让位"后，库的预览反而可以重新信任。

### D-24 容器交互重构：三动词 + 统一落位规则 + 纯函数路由

- **决策**（2026-10-14，大规模重构）：容器（节点背包/箱子）交互收敛为
  **三个动词**——放置（容器→树，永远 1 个）/ 收起（树→容器）/ 转移（容器↔容器），
  落位只有**一条规则**：空格/同类格=并入、异类格=交换、容器→树=放 1 个、树→容器=收起。
  实现分三层：`utils/tree-drop.ts`（DOM 读取）→ `utils/drop-action.ts`（纯函数路由，可单测）
  → `store.execDrop`（写模型）。
- **背景**：D-13~D-23 十一轮修补后，容器交互有 15 个 store 方法、两套交互文法、
  4 个近重复的「放置」实现、3 个「取出」实现、死代码（`handleChestDrop`/`takeOneFromChest`）
  与一个真 bug（箱子格右键误操作背包第 0 格）；同容器重排语义随几何变化（同列插入/跨列交换）。
- **做法**：
  - 容器从「3 个并排 Sortable 列」回到**单个扁平列表**（CSS 网格排版，D-23 的列拆分作废），
    格位固定：拖拽永不挤位，落点一律问指针；
  - 手势表见 docs/04 §3（单击/双击/滚轮/右键/拖拽）；「绑定落点」更名「**对侧**」；
  - 光标（右键拿起）扩展到箱子格（原 bug 即此处误接 `bagPick(0)`）；
  - 树→容器格 = 收进那个容器（`stow(nodeId, into)`）。
- **代价**：`execDrop` 成为容器写入的唯一入口（手势与拖拽共用）；旧 API
  （`applyDrop`/`moveSlot`/`moveInBag`/`chestStore`/`chestTake`/`transferWholeStack`/
  `bagClick`/`bagDoubleClick`/`bagWheel`/`bagPick`/`handleChestDrop`）全部删除，
  相关测试重写。
- **教训**：修补超过三轮就该找抽象，而不是找第 12 个特判。

### D-25 删除求值通道；手持 = 隐式实参

- **决策**（2026-10-14）：删除整套「求值通道」机制——`EvalKindKey`（`hand`/`node:<id>`/
  `class:<c>`）、候选序列、两轴处理器注册表（`handler(type, candidates)`）、
  内容包的 `EvalDef`/`evals` 字段、`EvalContext`/`EvalApi`，以及从未被内容使用的
  `chance`/`rng`/`setRet` 原语。
  替代方案只有一条规则：**手持物（选中格的类型）作为隐式实参参与被点节点的配方检测**
  ——先试「手持 + 子实参」签名，不中回落空手签名（手持永不打断已有配方）。
- **背景**：手持原本想做「多样化点击」，但检测发现它只可能作用于**被点的那一层**
  （内层永远是经典 eval 的静态值），两轴通道注册表对这个需求严重过度设计
  （~100 行引擎代码 + 一整套内容 API，零内容使用）。
- **后果**：
  - 「手持斧头点森林得木材」变成一条配方数据
    `{ at: 'forest', args: [{ item: 'axe' }], out: [{ item: 'wood' }] }`（已加入内容包做演示）；
  - 静态返回值（`[]` 显示）一律按**空手**计算（内层经典 eval）；
    `[?]` 的语义修订为「空手检测不通过」；
  - `toolClass` 保留，但只用于 UI 高亮（k-tool），不再参与求值；
  - 未来需要 chance/随机/结构原语时，按 03 篇 §5 四步流程重新引入。
- **教训**：机制要先有第二个用户再抽象；「手持改变点击」的正确最小实现是
  把手持塞进已有的签名匹配，而不是发明一套并行的派发表。

### D-26 从沙盒模型转向生产线模型：物品背包 + 选择面板建造 + 虚影放置 + 回收返还

- **决策**（2026-10-14，大规模重构）：放弃「节点背包」与 Minecraft 式沙盒交互，
  转向 Mindustry 式生产线模型：
  1. **资产只有物品（item）**：背包 = `物品 → 数量` 的表（容量按总数量计，`config.bagCapacity`）；
     没有「节点背包」、没有堆叠、没有格位。物品与节点类型 id 允许同名
     （`iron_ore` 既是背包里的物品，也是可放置的实参节点）。
  2. **建造 = 消耗物品**：侧栏「节点选择面板」列出全部节点类型与建造成本（`NodeDef.cost`）；
     点击进入**放置模式**——光标挂虚影节点、树里显示落点挤压预览；
     **左键 = 按落点建造**（扣成本、保持放置模式，可连续建造），**右键 / Esc / 再点同款 = 取消**；
     放置模式中左键不再触发 eval。
  3. **回收 = 全额返还**：节点 `×` 或拖到侧栏 → 返还全部建造成本（+箱子内容），子节点上移。
  4. **箱子变物品容器**：`物品 → 数量` + `config.chestCapacity`；交互简化为
     行单击转 1 / 双击整项（背包↔箱子），无拖拽。
  5. **配方产物全部是物品**（`out` 必须是物品 id），全部进背包——
     「节点类型 → 节点背包 / 资源 → 仓库」的双路由被删除。
- **背景**：D-13~D-24 的容器交互一直在跟「节点既是资产又是表达式」的双重身份搏斗
  （堆叠、槽位、跨容器拖拽、光标……11 轮 ADR）。生产线模型釜底抽薪：
  节点只存在于树上（表达式），资产只存在于背包里（物品），两者只在「建造/回收」处兑换。
- **代价**：
  - 存档 **v4**（`bag` 物品表；v3 的节点堆按建造成本折算迁移，资源直接并入）；
  - 删除整套容器拖拽设施（`drop-action.ts`、NodeBag/NodeSlot/Warehouse 组件、
    slotUnderPointer 等）与续转格/光标概念；
  - 手持改为「选中的背包物品行」；
  - Mindustry 式的连续放置要求点击语义随模式切换（放置 vs eval）。
- **教训**：当两个概念（节点/物品）的身份纠缠导致交互复杂度失控时，
  正确的解法不是更好的拖拽，而是把其中一个变成纯派生（建造 = 物品 → 节点的单向兑换）。

### D-27 回收 = 分解成原材料（30% 返还）+ 子级不折行、树区横向滚动

- **决策**（2026-10-14）：
  1. **回收不再是全额返还**：`×` 回收 = 把建造成本**分解成原材料**（沿「唯一产物是该物品」
     的配方实参递归下钻，`ItemDef.raw` 标记的原材料与无配方物品为止），再按
     `config.recycleRate`（默认 0.3）**向下取整**返还；箱子内容是玩家存货，原样返还。
  2. **子级列表不折行**：`.kids` 从 `flex-wrap: wrap` 改为 `nowrap` 单行延伸，
     超宽由 `.root-list`（`overflow-x: auto`）横向滚动；
  3. **拖拽/放置的边缘自动滚动**：真实拖拽用 SortableJS 自带 `scroll/scrollSensitivity/
scrollSpeed`；放置模式由视觉层 rAF 循环驱动（指针停在树区边缘 60px 内持续滚动，
     每帧重算落点）；滚轮在超宽时直接横滚。
- **背景**：折行让深层树「一行里套好几行」，视觉混乱；回收全额返还让「建了再拆」
  零成本，经济上没有损耗压力。
- **代价**：分解依赖内容配方的可逆性（要求产物唯一可反查；多产物配方不参与）；
  `mine` 之类低成本节点按 30% 取整后可能返还 0——平衡由内容侧调 `cost`/`recycleRate`。

### D-28 树布局改为纵向大纲（s-表达式 pretty-print）+ 自动折叠

- **决策**（2026-10-14）：
  1. **撤销 D-27 的横向滚动布局**：子列表从「横向单行」改为**纵向块级流**——每个节点占一行，
     层级 = 缩进（21px/层 + 层级竖线）。整个树就是 Lisp 代码的 pretty-print 排版。
     宽度 = 深度×缩进 + 一个 chip，**几乎不会横向溢出**；纵向随页面滚动（零学习成本），
     拖拽/放置全部退化成垂直列表的最简单场景（SortableJS 最佳支持 + 插入预览纯纵向）。
  2. **自动折叠（渐进披露）**：默认只展开前 `FOLD_DEPTH = 2` 层；更深的子树落地
     （拖拽到第 3 层及以下）默认折叠为 `+N` 徽标；调试面板提供「全部折叠/展开全部」。
  3. 放置模式的边缘自动滚动改为**滚页面**（指针停在视口上下边缘 60px 内，rAF 循环）；
     真实拖拽的窗口自动滚动由 SortableJS 默认处理。
- **背景**：折行（D-27 前）的乱源于兄弟子树高度交错无边界；横向滚动（D-27）的差源于
  「横向位置是看不见的隐藏状态」+ 拖拽/放置叠加位移。纵向大纲从根上消除横向维度。
- **代价**：视觉识别性从「一行表达式」变为「缩进代码」（大纲）；宽表达式变高（由自动折叠缓解）。

### D-29 Lisp 式渲染：表达式括号 + 括号把手 + 兄弟 inline 流式换行

- **决策**（2026-10-15，C→A 两步落地）：
  1. **括号 token**（C）：每个**表达式**（有实参的节点，或无实参的函数）渲染 `(` `)`——
     开括号在行首（chip 前），闭括号折叠/空函数时收在行内（`( f[?] )`、`…+N`），
     展开时内联在最后一个实参后面。符号（原子）不渲染括号。
  2. **括号 = 拖拽把手**（C）：开/闭括号与 chip 同为 SortableJS handle，
     拖任一括号 = 移动**整棵子表达式**（闭括号把手让长表达式从尾部拖成为可能）。
  3. **兄弟节点 inline 流式换行**（A）：`.kids > .node` 是 `inline-block` 原子盒，
     兄弟像 token 一样排满换行（浏览器原生断行，无自研排版引擎）；
     悬挂缩进保持固定 21px/层（宽度有界，不做 emacs 的「对齐开括号」——那会让宽度无界）。
     SortableJS 容器加 `draggable: '.node'`，括号 span 不是列表项。
  4. **树内拖拽落点权威修订**：SortableJS 的 **plan 优先**（树↔树都是普通容器，真实浏览器
     里可靠）；仅当 plan 退回源列表（跨列表 drop 被取消的征兆）而指针在别的列表上时，
     才用指针落点兜底。教训：合成/自动化事件流里 dragend 的坐标不可信，别让指针无条件覆盖。
- **背景**：D-28 的纯纵向大纲每节点一行、宽表达式很高；用户提出 emacs 式 Lisp 渲染。
  评估结论：完整「对齐开括号」的 pretty-print = 自研排版引擎（测量循环 + 宽度无界），不做；
  吸收其两个核心思想——括号让分组显形（治最初折行方案的乱）+ 括号是子表达式的把手。
- **代价**：换行由浏览器断行决定（不可控对齐）；括号 span 与 SortableJS 的列表项
  边界靠 `draggable` 选项隔离；CDP 类合成拖拽下 SortableJS plan 与指针坐标各有不可靠面。

### D-30 `()` 表示 eval：点击与 eval 解耦 + 括号即折叠 + 完全纵向大纲

- **决策**（2026-10-15）：
  1. **eval 属于括号**：只有「自己构成一个表达式」的节点（有实参 / 无实参的函数 / 根层落单
     节点——即渲染 `()` 的那些）点击才 eval 自己的 `(…)`；**裸符号实参点击没有效果**。
     根层落单节点也因此获得 `()`。点击与 eval 从此解耦（手持作为隐式实参只在真正 eval 时参与）。
  2. **括号即折叠开关**：删除独立 `[+]/[-]` 按钮——**点 `)` 折叠、点 `…+N` 徽标展开**；
     折叠形态完整保留括号 `( 头部[ret] …+N )`（修掉首版折叠后开括号消失的 bug）。
  3. **完全纵向大纲**：撤销 D-29 的兄弟 inline 流式换行与「≤3 子节点横向」的紧凑模式——
     每个表达式 = `( 头部` 一行 + 实参逐行 + 闭括号行（emacs 风格）；**删除层级竖线**，
     嵌套由「括号 + 悬挂缩进 21px/层」表达。
- **背景**：用户实测反馈——竖线不自然；括号做折叠按钮是对的但折叠后括号消失了；
  混合横纵向（含 ≤3 紧凑规则）让展开/收起时的重排不可预期（兄弟「没动」的观感），
  大道至简回到完全纵向。
- **代价**：宽表达式行数更多（自动折叠缓解）；D-29 的 inline 流与 FLIP 挤压动画保留给
  放置 ghost（横向挤压在纵向大纲里自然不再出现）。

### D-35 回收 = 返还 cost × 返还率（撤销 D-27 的「分解成原材料」）

- **决策**（2026-10-15）：回收返还**建造成本本身 × `config.recycleRate`**（默认 0.3），
  Decimal 精确折算（允许小数：装配台 钢板×3+铁×2 → 钢板×0.9 + 铁×0.6）。
  **删除整套递归分解机制**：`decomposeCost` / `DecomposeCtx` / 注册表 `decomposeRecipeOf`
  反查索引 / `ItemDef.raw` 标记——全部不存在了。
- **背景**：D-27 的「分解成原材料」要求把 cost 里的中间物品（铁/钢板）逆着配方拆回
  矿/煤/氧，于是需要「反查唯一产物是它的配方」这条消歧规则（多产物配方无法逆推）+ raw
  终点标记 + 递归 + 环保护。实测效果荒谬：回收装配台返还的是**煤**。物品只由节点产出，
  不存在「物品的分解」；回收该返还的就是 cost 本身打折。
- **代价**：返还物品可能出现小数（背包本就 Decimal 原生）；`fmt` 展示为 `0.9` 这类。
- **教训**：为「返还什么」引入一套配方逆推 = 把配方的单射假设塞进数据模型；
  需求是「打折退回」，一条乘法就够了。
